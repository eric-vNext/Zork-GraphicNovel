## Workflow: use `utils/` before every ship

Two scripts were added this session specifically so future sessions don't
re-derive the verify/deploy loop by hand:

- **`utils/verify.sh`** — runs `tsc --noEmit`, `vitest run`, and
  `npm run build` from `game/`, in the same order CI runs them. Run this
  before every commit that touches `game/src` or `game/tests`. A clean run
  here means the CI build/test job will also pass.
- **`utils/watch-deploy.sh [branch]`** — finds the latest GitHub Actions
  "Deploy to GitHub Pages" run for the branch (defaults to current branch)
  and streams it to completion via `gh run watch --exit-status`. Run this
  right after `git push` instead of manually polling `gh run list`.

Typical ship sequence:

```
./utils/verify.sh          # local typecheck + tests + build
git add -A && git commit -m "..."
git push
./utils/watch-deploy.sh    # confirm CI build+test+deploy succeeded
```

CI (`.github/workflows/deploy.yml`) runs `npm test` and `npm run build`
itself before deploying, so a broken build cannot reach GitHub Pages — but
`verify.sh` catches failures ~2 minutes sooner and without waiting on
Actions.

## Testing patterns already in place

- **`game/tests/testUtils.ts`** — shared test helpers:
  - `txt(g, cmd)` — runs a command, returns joined text-event output.
  - `fightUntilWon(g, room, winFlag, attackCmd, attempts=60)` — snapshots
    state, attacks in a loop, and **restores the snapshot and retries** if
    the player dies or leaves the fight room. Combat is genuinely
    probabilistic (ported RNG-driven melee tables with a fixed seed), so a
    fixed iteration count can legitimately fail when the player dies and
    gets resurrected elsewhere mid-loop. **Always use this helper (or the
    same snapshot/retry pattern) for any test that needs to "eventually
    win a fight"** — don't assert on a bare attack loop.
- The RNG is a deterministic xorshift32 with a fixed seed (12345) per
  `Game` instance. Any change that adds/removes an `rng()` call anywhere in
  a code path shifts the entire subsequent random sequence. If tests
  suddenly start failing after an unrelated-seeming change, suspect this
  before suspecting game logic — check whether the change added or removed
  a `rng()` call count.

## Known architecture gotcha: "last panel event wins"

Multiple call sites emit a dramatic event panel (`events/...`) and then a
room-transition panel (`rooms/...`) fires afterward and silently
overwrites it, because the panel renderer just takes the last `panel`
event in a turn. This has already bitten window-entry, boat-launch,
bat-abduction, prayer-teleport, and first-entry troll combat (fixed via a
`justArrived` one-turn grace flag in `WorldState`, set in `enterRoom()` and
checked in `fightDaemon()`). **When adding any new dramatic/event panel
that fires during a move/transition, emit it after the room-transition
panel, not before** — or it will be silently discarded.
